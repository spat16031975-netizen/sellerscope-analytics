# Безопасность

## Основные правила

- секреты приложения хранятся только в Railway Variables;
- учётные данные магазинов шифруются AES-256-GCM отдельным data key; в БД хранятся ciphertext, nonce/tag и `credentialKeyId`;
- мастер-ключ не находится в PostgreSQL и репозитории;
- OAuth Ozon предпочтительнее долгоживущих ручных ключей;
- токены никогда не возвращаются браузеру и маскируются в структурированных логах;
- HTTPS обязателен; cookies сессии имеют `HttpOnly`, `Secure`, `SameSite=Lax`;
- каждый запрос проверяет сессию, membership и роль на сервере;
- административные действия и доступ к подключениям пишутся в `AuditEvent`;
- журнал ошибок хранит код, request ID площадки и безопасное сообщение, но не тело с секретом.

## Защита от доступа к чужой организации

Нельзя выполнять `findUnique({ id })` для tenant-данных без последующей проверки. Используется фильтр `{ id, organizationId }` или связь через проверенный `store.organizationId`. ID из URL не определяет организацию. Автотест `src/security/tenant.test.ts` покрывает подмену параметра; интеграционные тесты БД должны повторить сценарий для каждой API-группы.

## OAuth

`state` одноразовый, случайный и связан с сессией; callback принимает только заранее зарегистрированный redirect URI. Access token обновляется сервером. Refresh token ротируется, предыдущая версия удаляется после успешного обновления. Отзыв доступа переводит Connection в `REVOKED`.

## Минимальные права

Для аналитики запрашиваются только read-only scopes. Любые методы изменения карточек, ставок или заказов исключены из первого релиза.

## Реакция на инцидент

Отключить соединение, отозвать токен у площадки, ротировать ключ шифрования, проверить AuditEvent и безопасные request ID, уведомить затронутую организацию, задокументировать причину и восстановление.
